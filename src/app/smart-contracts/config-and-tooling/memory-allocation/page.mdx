# Memory Allocation

Klever smart contracts are compiled into WebAssembly (Wasm), which does not inherently provide memory allocation capabilities. Typically, WebAssembly programs require specialized memory allocation functionality to work with the heap.

However, using traditional memory allocation methods is strongly discouraged on Klever for several reasons:

1. **Managed Types**: Klever introduces "managed types" that are handled by the VM, offering a more efficient and reliable alternative to traditional memory allocation.

2. **Memory Growth Operations**: Memory growth operations in WebAssembly can be both costly and unpredictable. To ensure the stability of the blockchain, Klever has chosen to limit these operations significantly.

3. **Contract Code Bloating**: Memory allocators can add unnecessary bulk to smart contract code, introducing elements unrelated to the contract's specifications, which goes against Klever's design philosophy.

Despite these reasons, it is not entirely reasonable to prohibit the use of allocators altogether, as the decision should ultimately be left to developers. Before framework version 0.41.0, the only allocator solution available was `wee_alloc`. Unfortunately, this allocator had not been maintained for a few years and had known vulnerabilities. It also triggered critical warnings from GitHub's Dependabot for all contract projects, even when most of them did not actively use it.

To address these concerns, Klever implemented the following changes:

1. **Configurable Allocators**: Developers can now configure allocators from the `multicontract.toml` file, which serves as the main source of contract build specifications. This provides flexibility and choice to developers.

2. **New Allocators**: Klever introduced new allocators in the framework, offering alternatives to `wee_alloc`. These allocators are:
   - `FailAllocator` (Default): This allocator simply crashes whenever any memory allocation or deallocation is attempted. It effectively prevents accidental memory allocation and enforces strict memory management.

   - `StaticAllocator64k`: This allocator pre-allocates a static 64 KiB buffer where all memory is allocated. It never calls memory.grow and crashes when the buffer is full. This allocator may be suitable for small contracts with limited data processing needs, aiming to avoid the complexities of memory growth.

   - `LeakingAllocator`: This allocator uses memory.grow to obtain memory pages and, like the others, never deallocates memory. This is because contracts typically do not consume excessive memory, and all memory is cleared at the end of execution. It is suitable for contracts with slightly larger data requirements.

   - `wee_alloc` (Still Supported): While not included in the framework by default, `wee_alloc` is still supported. Contracts can explicitly import it if needed.

## VM Memory Limits

The Klever VM limits how much linear memory a contract can declare and how often it can grow it. Wasm memory is counted in pages of 64 KiB. Three separate limits apply:

| Limit                                  | Current value       | Where it comes from                                      | What happens when it is exceeded                                                                |
| -------------------------------------- | ------------------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `memory.grow` calls in one call        | 10                  | Gas schedule, `WASMOpcodeCost.MaxMemoryGrow`             | The call fails with `VMExecutionFailed` ("memory limit reached") and **keeps its full gas fee** |
| Pages requested by one `memory.grow`   | 1                   | Gas schedule, `WASMOpcodeCost.MaxMemoryGrowDelta`        | The call fails with `VMExecutionFailed` ("memory limit reached") and **keeps its full gas fee** |
| Memory declared by the contract module | 20 pages (1.25 MiB) | Constant in the VM executor (`MAX_MEMORY_PAGES_ALLOWED`) | The deploy fails: the VM rejects the code as invalid contract code                              |

Each successful `memory.grow` also costs gas: currently 1,000,000 (`WASMOpcodeCost.MemoryGrow`).

### Exceeding the grow limits fails the call

The Wasm specification says that `memory.grow` returns `-1` when it cannot grow memory. On Klever this is **not** what happens when a contract exceeds `MaxMemoryGrow` or `MaxMemoryGrowDelta`. The VM stops the contract with a memory-limit breakpoint, and the transaction fails with result code `VMExecutionFailed` and the internal VM error `memory limit reached`. The fee paid for the call's gas limit is not returned, and the contract cannot catch the failure and recover. The 11th grow fails even if the first ten succeeded, and so does a single `memory.grow(2)`.

The fee estimator (`/transaction/estimate-fee`, used by wallets and `operator` before sending) runs the call first and rejects it with `VMExecutionFailed`, so an over-limit call normally fails before it is broadcast. If it is broadcast anyway, it fails on-chain as described above.

`memory.grow` still returns `-1` in one case: when the grow stays within the Klever limits but goes past the maximum that the module itself declares. The call does not fail; what the contract does next depends on its allocator.

### What the 20-page limit covers

The 20-page limit is checked against the memory section of the compiled `.wasm`: the declared maximum, or the declared initial size when the module declares no maximum. A module over the limit cannot be deployed: the fee estimator rejects it as `ContractInvalid` (invalid contract code), and a deploy broadcast anyway fails on-chain with the same internal error.

The limit does not cap memory after later `memory.grow` calls. A module that declares 20 pages and no maximum can grow 10 times and reach 30 pages (1.875 MiB) in one call.

To see what your contract declares, inspect the memory section of the build output, for example with [wabt](https://github.com/WebAssembly/wabt):

```bash
wasm-objdump -x output/<contract>.wasm | grep -A1 "Memory\["
```

### Read the live values, do not hard-code them

`MaxMemoryGrow`, `MaxMemoryGrowDelta` and `MemoryGrow` are gas schedule values. The gas schedule is selected per epoch by the `gasScheduleByEpochs` entry in the node's `enableEpochs.yaml`, which ships with each release, so a release can change them; mainnet currently uses [`gasScheduleV1.yaml`](https://github.com/klever-io/klever-go/blob/develop/config/node/gasScheduleV1.yaml). The 20-page limit is fixed in the VM executor and changes only with a new executor version. None of these limits can be changed by a governance proposal.

Do not build contract logic around the numbers above. Check the gas schedule for the release you deploy on, and design contracts to stay well under the limits, ideally with managed types and no heap allocation at all (see [Dynamic Allocation](/smart-contracts/best-practices/dynamic-allocation)).
