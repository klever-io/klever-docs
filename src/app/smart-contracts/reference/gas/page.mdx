# Gas and Fees

Every call to a smart contract runs on a gas budget. The Klever VM (KVM) charges gas for the code it loads, every WebAssembly instruction it executes, every host function the contract calls and the bytes it reads, copies and stores. This page explains how those charges add up, how gas turns into the KLV fee you pay, and lists the current cost of every operation.

The costs come from the network's **gas schedule**, a configuration file (`gasScheduleV1.yaml`) that ships with each node release. The tables at the end of this page are generated from it.

## How a call is charged

When a transaction calls a contract, the VM charges gas in this order:

1. **Loading the code.** A flat `GetCode` cost plus `AoTPreparePerByte` for every byte of the contract's `.wasm`. This is paid on **every call**, not only on deploy, so a larger contract costs more to call even if the function you call is tiny.
2. **Executing instructions.** Each WebAssembly instruction that runs pays its cost from `WASMOpcodeCost`.
3. **Host functions.** Each call into the VM API (reading arguments, storage, big integers, managed buffers, hashing, transfers) pays its own cost, plus per-byte costs for the data it moves.
4. **Storage.** Reads and writes to the contract's storage pay host function costs that depend on how many bytes are involved.

If the gas runs out at any point, the call stops. See [Running out of gas](#running-out-of-gas).

Deploying or upgrading a contract is charged differently from a call: `CreateContract` plus `CompilePerByte` for every byte of code, instead of `GetCode` and `AoTPreparePerByte`.

### Instructions: linear in what you execute

Gas metering is injected into the contract's WebAssembly when the VM compiles it. Every instruction that executes pays its cost from the `WASMOpcodeCost` section, so pure computation costs gas in proportion to the number of instructions executed, weighted per instruction:

| Kind of instruction                                                            | Typical cost |
| ------------------------------------------------------------------------------ | ------------ |
| Control flow, locals, globals, loads, stores, integer add/sub/mul, comparisons | 5            |
| Integer division and remainder (`i32.div_s`, `i64.rem_u`, …)                   | 18           |
| Bit counting (`clz`, `ctz`, `popcnt`)                                          | 100          |
| `memory.grow`                                                                  | 1,000,000    |

A loop that runs 1,000 times costs about 1,000 times the gas of its body. There is no discount for repeated code and no surcharge that grows with the number of iterations.

The schedule lists a cost for every opcode the WebAssembly engine knows, including families a contract cannot use: the VM forbids floating-point operations (see [The Klever VM](/klever-vm#fast-execution-engine)), so those entries are never charged in practice.

### What is not per-instruction

Most of the gas in a real call is not spent on instructions. These charges follow other rules:

- **Code loading.** `GetCode` (1,000,000) plus `AoTPreparePerByte` (100) per byte of code, on every call. A 50 KB contract pays about 6,000,000 gas before its first instruction runs. Code size is a cost on every call: keep `wasm-opt` on (it is by default, see [Build Reference](/smart-contracts/config-and-tooling/build-reference)) and avoid pulling in code the contract does not need.
- **`memory.grow`.** A flat 1,000,000 per call, whatever the number of pages. The VM also limits how often and how much memory can grow; see [VM Memory Limits](/smart-contracts/config-and-tooling/memory-allocation#vm-memory-limits).
- **Host functions.** Each one has a fixed cost per call from its API group: `BaseOpsAPICost`, `ManagedBufferAPICost`, `BigIntAPICost`, `BigFloatAPICost`, `ManagedMapAPICost`, `CryptoAPICost`, `EthAPICost`. When the function moves data between the VM and the contract, it also pays `DataCopyPerByte` (50) for each byte.
- **Storage reads.** Priced by a curve; see the next section.
- **Storage writes.** The host function cost (`StorageStore`, `MBufferStorageStore`: 75,000) plus a per-byte cost that depends on what the write does:
  - a new value, or the bytes a value grows by: `StorePerByte` (10,000) per byte;
  - the bytes of the existing value being overwritten: `PersistPerByte` (1,000) per byte;
  - writing exactly the value already stored: `DataCopyPerByte` (50) per byte;
  - storage keys longer than 32 bytes pay `DataCopyPerByte` for each extra byte.

  `ReleasePerByte` is in the schedule but is not charged or refunded today: shrinking or deleting a value does not give gas back.

- **Logs and return data.** `PersistPerByte` per byte of event data and of data a contract returns, on top of the host function cost.
- **Big integers longer than 32 bytes.** `CopyPerByteForTooBig` (1,000) per byte, when the value is copied or operated on.
- **Built-in functions.** Protocol operations a contract triggers, such as a transfer or a freeze, cost what `BuiltInCost` lists (`Transfer`: 200,000).

### Storage reads

A storage read that is not served from the VM's cache is priced by a curve on the depth `d` of the key in the state trie:

```
cost(d) = a·d² + b·d + c
```

with `a` = 688, `b` = 31,858 and `c` = 15,287 in the current schedule. If the curve gives less than `MinimumGasCost` (1,000), the read is charged the host function's fixed storage-load cost instead. The node checks the coefficients when it loads the schedule: `a` must be positive, `c` must not be negative, and the curve must not decrease for positive depths.

The node currently reports a depth of 0 for every read, so **every uncached storage read costs `c` = 15,287 gas** plus `DataCopyPerByte` for the bytes read. A read served from the VM's storage cache costs `CachedStorageLoad` (1,000) instead.

The fixed `StorageLoad` costs in `BaseOpsAPICost` (50,000) are not added to this: the curve replaces them.

### Per-transaction limits

Some limits are counts, not gas. One transaction, including every contract it calls, may make at most:

| Limit                       | Current value |
| --------------------------- | ------------- |
| Built-in function calls     | 100           |
| Token transfers             | 250           |
| Storage reads from the trie | 1,500         |

Going over any of them fails the call with `max calls reached` (`too many built-in functions calls`, `too many KDA transfers` or `too many reads from trie`), with the same consequences as running out of gas.

## Running out of gas

If a call needs more gas than its limit, at any point, it fails with result code `VMOutOfGas`. The same happens before execution starts if the gas limit cannot even pay for loading the code.

A failed call, out of gas or for any other reason:

- **changes nothing.** The VM keeps its changes to storage and balances in memory and only applies them when the call succeeds, so a failed call leaves no partial state.
- **consumes its whole gas limit,** not only the gas spent before it failed.
- **keeps the fee.** The transaction is included in a block and its fee is paid.

The fee estimator (`/transaction/estimate-fee`) runs the call before you send it, so a call that would run out of gas or fail is normally rejected before it is broadcast.

## How gas becomes the fee

Klever has no gas price. A transaction pays two fees in KLV, both set when the transaction is built and both charged in full:

| Fee            | What it pays for                                  | How it is computed                                                      |
| -------------- | ------------------------------------------------- | ----------------------------------------------------------------------- |
| `kAppFee`      | The operation itself                              | The network parameter `KAppFeeSmartContract`                            |
| `bandwidthFee` | The transaction's size **and** the contract's gas | (data bytes + 250) × `FeePerDataByte`, **plus** what you add to buy gas |

The gas limit of a contract call is whatever the bandwidth fee pays for beyond the size of the transaction:

```
minimum bandwidth fee = (data bytes + 250) × FeePerDataByte
gas limit             = (bandwidthFee − minimum bandwidth fee) × GasMultiplier
```

The fees are in KLV's smallest unit (1 KLV = 1,000,000 units). `GasMultiplier`, `FeePerDataByte` and `KAppFeeSmartContract` are network parameters, changed by governance proposal; read the current values from the API (`/v1.0/network/network-parameters`):

| Parameter              | Mainnet     | Testnet     |
| ---------------------- | ----------- | ----------- |
| `GasMultiplier`        | 1           | 1           |
| `FeePerDataByte`       | 8,000       | 1           |
| `KAppFeeSmartContract` | 2,000,000   | 2,000,000   |
| `MaxGasPerTX`          | 400,000,000 | 400,000,000 |

With `GasMultiplier` at 1, each unit of bandwidth fee above the minimum buys one unit of gas, so **1 gas costs 0.000001 KLV**. A gas limit above `MaxGasPerTX` is rejected.

**Unused gas is not refunded.** The whole bandwidth fee is charged whatever the call actually used. Set the gas limit close to what the call needs: the fee estimator returns `gasEstimated` (the gas the simulated call used, plus `GasMultiplier`) and a `safetyMargin` of 10% of it, to size the bandwidth fee from.

## Worked example

Testnet transaction [`b07188cf…3f3242`](https://testnet.kleverscan.org/transaction/b07188cf445bfa2112188112445d1889a35c1aa399ce28e43a09e346ba3f3242) calls `commitDrawSecret` on contract `klv1qqqqqqqqqqqqqpgqgrwndcmtwhl9hjldaa6tcyk6qxvl8w23770s9mx5vs`. You can read it from a node with `GET /transaction/b07188cf445bfa2112188112445d1889a35c1aa399ce28e43a09e346ba3f3242?withResults=true`.

**What the sender paid.** The data field is 89 bytes and the transaction has one contract, so on testnet (`FeePerDataByte` = 1):

| Item                  | Value                                                                           |
| --------------------- | ------------------------------------------------------------------------------- |
| `kAppFee`             | 2,000,000 (2 KLV)                                                               |
| `bandwidthFee`        | 12,849,346 (12.849346 KLV)                                                      |
| Minimum bandwidth fee | (89 + 250) × 1 = 339                                                            |
| Gas limit             | (12,849,346 − 339) × 1 = **12,849,007** (the node reports `GasLimit: 12849007`) |

**What the call used.** The transaction's `totalConsumedGas` log event carries the gas used, hex `6f6568` = **7,300,456**. It splits into:

| Part                                                                       | Gas           |
| -------------------------------------------------------------------------- | ------------- |
| Code loading: `GetCode` 1,000,000 + 57,958 bytes × `AoTPreparePerByte` 100 | 6,795,800     |
| Execution: instructions, host functions, storage reads and writes, logs    | 504,656       |
| **Total (`totalConsumedGas`)**                                             | **7,300,456** |

The contract's code is 57,958 bytes: the code of its last upgrade before this call, whose hash matches the account's `CodeHash`. Loading it costs 93% of the gas used. The function itself, which reads and writes a few storage values (an uncached read alone is 15,287 gas and a host call to store a value 75,000 plus per-byte costs), costs the remaining 504,656.

**What it cost.** The sender paid 2 + 12.849346 = **14.849346 KLV**. The call used 7,300,456 gas, about 7.3 KLV of the bandwidth fee; the other 5,548,551 units of gas limit were paid for and not refunded. A bandwidth fee built from the estimator (gas used plus 10%) would have been about 8.03 KLV.

To regenerate the tables after a gas schedule update, download the current mainnet configuration package and run the generator with the package number and the date:

```bash
mkdir -p /tmp/klever-config
curl -sS https://backup.mainnet.klever.org/config.mainnet.108.tar.gz | tar -xz -C /tmp/klever-config
pnpm run gen:gas-tables /tmp/klever-config/config/gasScheduleV1.yaml 108 2026-11-06
```

Which schedule file a network uses, from which epoch, is set by `gasSchedule.gasScheduleByEpochs` in the package's `enableEpochs.yaml`. Mainnet package 108 uses `gasScheduleV1.yaml` from epoch 4860; testnet package 109 switched to the same file at epoch 32945.
