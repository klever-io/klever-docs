# API & SDK

Useful links and info for devs that want to integrate the Klever Blockchain to their projects

## JavaScript SDK

To build a web or Node.js application that communicates with the Klever Blockchain, use the [Klever JavaScript SDK](/javascript-sdk). It provides a unified API for browser dApps (via Klever Extension or mobile wallet) and backend services.

## Checking the status of the transaction

When you broadcast a transaction, you will receive it's unique hash.

Take the hash `7b066e58b650d4ea6ba61de087350ddf909cfee660cc9537c0167b38df6d4882 `for example.

You can either see the transaction details [using the Klever Explorer](https://kleverscan.org/transaction/7b066e58b650d4ea6ba61de087350ddf909cfee660cc9537c0167b38df6d4882) or by calling one of the api endpoint's.

[Using the proxy api call](https://api.mainnet.klever.org/v1.0/transaction/7b066e58b650d4ea6ba61de087350ddf909cfee660cc9537c0167b38df6d4882), you will receive the parsed transaction as response.

[Using the node api call](https://node.mainnet.klever.org/transaction/7b066e58b650d4ea6ba61de087350ddf909cfee660cc9537c0167b38df6d4882), you will receive the transaction as it is in the blockchain.

Using the explorer or the proxy api, you can check the status code of the transaction, if it matches the expected format it will be "`success`".

If, for some reason, your transaction was broadcast but doesn't appear in the proxy api or in the explorer, you can check its status in the node api. It will help you identify if the node that you used to broadcast the transaction is faulty.

## Sending a transaction to the Klever Blockchain

Sending a transaction involves three steps: **building**, **signing**, and **broadcasting**.

### Using the JavaScript SDK

The [Klever JavaScript SDK](/javascript-sdk) handles all three steps automatically:

```typescript
import { KleverProvider } from '@klever/connect-provider'
import { BrowserWallet } from '@klever/connect-wallet' // or NodeWallet for backend
import { parseKLV } from '@klever/connect-core'

const provider = new KleverProvider('mainnet')
const wallet = new BrowserWallet(provider)
await wallet.connect()

const result = await wallet.transfer({
  receiver: 'klv1receiver...',
  amount: parseKLV('10'),
})
console.log('Transaction hash:', result.hash)
```

See the [Web App guide](/javascript-sdk/web-app) or [Node.js guide](/javascript-sdk/node-js) for more examples.

### Using the raw API

If you need to interact with the blockchain endpoints directly:

**1. Build** — POST to the [`/transaction/send` endpoint](https://node.mainnet.klever.org/swagger/index.html#/Transaction/post_transaction_send) and receive an unsigned transaction as response.

**2. Sign** — Use the [Go SDK](https://github.com/klever-io/klever-go-sdk) or the [Node.js SDK](/javascript-sdk/node-js) to sign without exposing your private key in the browser.

**3. Broadcast** — POST the signed transaction to the [`/transaction/broadcast` endpoint](https://node.mainnet.klever.org/swagger/index.html#/Transaction/post_transaction_broadcast) to be processed and validated by the blockchain.

## Multisig API reference

The Multisig API stores a transaction while its cosigners collect signatures. It does not broadcast on its own: once the collected weight reaches the permission threshold, the client calls `POST /broadcast/{hash}`. It is available at `https://multisign.mainnet.klever.org` and `https://multisign.testnet.klever.org`.

### 1. Create a transaction

- Build the transaction with the node (`POST /transaction/send`) or with an SDK, using the multisig account as `sender` and a valid `permissionID`.
- Send it to `POST /transaction` together with its `hash`. The `hash` is the transaction hash the node returns: the hex encoding of the 32-byte Blake2b-256 digest of `RawData`. The API recomputes it from the `raw.RawData` you send and rejects the request when they differ, so the raw data and the signatures are always bound to the same hash. A `0x` prefix is not accepted.
- The transaction is stored under its lower-case hash, which the response returns: `{"status": "OK", "hash": "<lower-case hash>"}`. Upper-case hex is accepted on every endpoint and converted to lower case.
- The first request may carry no signatures: it creates the pending transaction, stored with the permission addresses and weights.

<Note color="yellow">
    **Signatures are verified against the hash.** Every signature must be an ed25519 signature of the 32-byte hash, made by one of the addresses of the permission. A request whose `hash` does not match its `raw.RawData`, or that carries a signature from a key outside the permission, is rejected and nothing is stored.
</Note>

### 2. Add signatures

- Each cosigner signs the hash with their key and sends it to the same `POST /transaction` endpoint, with the same `hash` and `raw.RawData` and their signature in `raw.Signature`.
- Once the transaction is stored, every request must bring at least one new signature. Sending the signatures already collected together with yours is fine: the known ones are ignored and the new one is merged. A request that brings nothing new, whether it repeats stored signatures or carries none, is rejected.
- The request is read from `hash` and `raw` only. `address`, `signers` and `threshold` in the body are ignored; which signers are marked as signed is decided from the signatures themselves.
- You can list the transactions, and signers by hash or address.

### 3. Broadcast

- When the weight of the collected signatures reaches the permission threshold, call `POST /broadcast/{hash}`. Before that, the request is rejected with `transaction is not fully signed yet`.
- The transaction joins a queue per sender account and is sent to the network in nonce order. A `200` means it was queued; a temporary failure to reach the network is retried by the API and is not reported to the caller.
- A hash that is not stored also returns `200` and does nothing. Check it with `GET /transaction/{hash}` first.

### Delete a pending transaction

- Any signer listed on the pending transaction can remove it with `DELETE /transaction/{hash}`, whether or not they have signed it yet. Deleting drops every signature collected so far.
- The request must carry a **delete proof**: an ed25519 signature, by one of those signers, over `Blake2b-256("klever-multisign:delete:" || hash)`, where `hash` is the 32 raw bytes of the transaction hash (not its hex). Send it as hex in the body: `{"signature": "<hex>"}`.
- Pending Tron transactions cannot be deleted through the API; they are removed when broadcast or when they expire.

<Note color="yellow">
    **Do not sign the transaction hash itself.** The cosignatures stored on a pending transaction are signatures over its hash, and anyone can read them with `GET /transaction/{hash}`. The API accepts only a signature over the delete message above, so a cosignature can never be used to delete a transaction.
</Note>

Example in Go. A Klever private key is the 32-byte ed25519 seed. A Klever PEM file holds 64 bytes, the seed followed by the public key, so the seed is its first 32 bytes; the Go SDK's `PrivateKey()` already returns the seed. `ed25519.Sign` needs the expanded key, so derive it with `ed25519.NewKeyFromSeed` first:

```go
txHash, _ := hex.DecodeString(hashHex) // 32 bytes
msg := blake2b.Sum256(append([]byte("klever-multisign:delete:"), txHash...))
key := ed25519.NewKeyFromSeed(seed) // seed: 32 bytes (the first 32 of a PEM key)
signature := hex.EncodeToString(ed25519.Sign(key, msg[:]))
// DELETE /transaction/{hashHex} with body {"signature": signature}
```

### Errors

Errors are returned as `{"error": "<reason>"}` unless the table says the body is empty.

| Endpoint | Status | Reason |
|---|---|---|
| `POST /transaction` | `400` | `json: Error marshalling json` (the body is not valid JSON), `invalid transaction data: missing raw data, sender or contract`, `invalid transaction hash: must be the 32-byte hash of the raw data`, `invalid signature`, `address has already signed this transaction`, `permission id not found on sender account` |
| `POST /broadcast/{hash}` | `400` | `failed to validate request`, `invalid transaction hash: must be the 32-byte hash of the raw data`, `transaction is not fully signed yet`, `transaction nonce is lower than account nonce`, `another pending transaction with the same nonce already exists` |
| `GET /transaction/{hash}` | `400` | `failed to validate request`, `invalid transaction hash: must be the 32-byte hash of the raw data` |
| `GET /transaction/{hash}` | `404` | No transaction is stored under this hash. Empty body. |
| `GET /transaction/by-address/{address}` | `400` | `json: Error marshalling json` (the address does not pass validation) |
| `GET /transaction/by-address/{address}` | `204` | No transaction is stored for this address. Empty body. |
| `DELETE /transaction/{hash}` | `400` | `failed to validate request`, `invalid transaction hash: must be the 32-byte hash of the raw data`, `missing signature: sign the delete proof of the transaction hash with a listed signer's key`, `invalid signature` (malformed, or not a delete proof by a listed signer), `deleting a Tron transaction requires a signature scheme that is not supported yet` |
| `DELETE /transaction/{hash}` | `404` | `transaction not found` |
| `POST /transaction`, `POST /broadcast/{hash}` | `500` | `cannot find account in database`: the `sender` account does not exist on chain. Retrying does not help; the account must exist (receive a transfer) first. |
| Any | `500` | The API could not reach its storage or the blockchain. The body carries the underlying error. |

## Websocket Reference

A Klever node pushes blocks, transactions and account changes over a WebSocket at `/subscribe`. On the same connection you can also query a block or a transaction and change your subscriptions without reconnecting.

### Endpoints

| Network | Chain ID | URL |
| ------- | -------- | --- |
| Mainnet | `108` | `wss://node.mainnet.klever.org/subscribe` |
| Testnet | `109` | `wss://node.testnet.klever.org/subscribe` |

The public endpoints need no authentication and are shared by everyone. For a workload that cannot miss events or depend on a shared service, run your own node with the indexer enabled and connect to its `ws://localhost:8080/subscribe`. See [How to Set Up Your Own Indexer](/node-operations#how-to-set-up-your-own-indexer) and [Securing the node API](/node-operations/securing-the-api).

`/subscribe` has no API key. The only authentication a node can require is HTTP Basic Auth on the WebSocket upgrade, when its operator sets the route to `secured: true`, as the securing page recommends for a node reachable from other machines. The examples below send no credentials: to use them against such a node, add an `Authorization: Basic ...` header to the connection request.

### Connecting

1. Open a WebSocket connection to the endpoint.
2. Send the subscription message as the first message, within 30 seconds.
3. Read the events the node pushes.

The subscription message:

```json
{
  "addresses": [],
  "subscribed_types": ["blocks"]
}
```

| Field | Description |
| ----- | ----------- |
| `subscribed_types` | The event types to receive. Must contain at least one type from the table below. |
| `addresses` | The `klv1...` addresses to watch. Used by `accounts` and `user_transactions`; send `[]` when you subscribe only to `blocks` or `transactions`. |

### Subscription types

| Type | Needs `addresses` | What you receive |
| ---- | ----------------- | ---------------- |
| `blocks` | No | Every new block. |
| `transactions` | No | Every transaction on the network, grouped by block. |
| `accounts` | Yes | The new state of a watched account each time it changes. |
| `user_transactions` | Yes | Each transaction a watched address sends or receives. |

You can combine any of the four types in one connection. `accounts` and `user_transactions` deliver nothing until you give them at least one address, in the same message that names the type. Types and addresses pair up only inside one message: the `subscribe` request below explains what that means when you add subscriptions later.

### Events

Every event the node pushes has the same envelope:

```json
{
  "type": "blocks",
  "address": "",
  "hash": "",
  "data": {}
}
```

| Field | Description |
| ----- | ----------- |
| `type` | The subscription type that produced the event. |
| `address` | The watched address, for `accounts` and `user_transactions`. Empty for `blocks` and `transactions`. |
| `hash` | Empty in events sent to clients. Read the block or transaction hash from `data.hash`. |
| `data` | The payload. Its shape depends on `type`, as shown below. |

The samples below are shortened: long hex strings are cut and some fields are left out. Timestamps in events are in milliseconds.

### Requests

After the subscription message you can send requests at any time. Each request carries an `id` you choose, a `method` and its `params`:

```json
{
  "id": "1",
  "method": "get_block",
  "params": { "nonce": 34623521 }
}
```

The reply repeats your `id`, so you can match replies to requests when several are in flight. It carries `data` on success or `error` on failure:

```json
{ "id": "1", "data": {} }
```

```json
{ "id": "1", "error": "must provide nonce or hash" }
```

Replies and events share the connection. A message with an `id` field is a reply; a message with a `type` field is an event.

#### `get_transaction`

Returns a transaction by hash.

| Param | Required | Description |
| ----- | -------- | ----------- |
| `hash` | Yes | The transaction hash. |
| `withResults` | No | Include receipts and logs. Defaults to `false`. |

```json
{
  "id": "2",
  "method": "get_transaction",
  "params": {
    "hash": "914a6febfe3fb4a2fe28f3b2a491d320a6da3323163d138723c31e67d07008d8",
    "withResults": true
  }
}
```

#### `get_block`

Returns a block by nonce or by hash. If you send both, the nonce is used.

| Param | Required | Description |
| ----- | -------- | ----------- |
| `nonce` | One of `nonce` or `hash` | The block nonce (height). |
| `hash` | One of `nonce` or `hash` | The block hash. |
| `withTxs` | No | Include the block's transactions. Defaults to `false`. |

```json
{
  "id": "3",
  "method": "get_block",
  "params": { "nonce": 34623521, "withTxs": false }
}
```

<Note>
  `get_block` and `get_transaction` return the same format as the node's REST API, which is not the format of the pushed events: the block fields sit under `Header` with capitalized names, byte fields are base64, and `Timestamp` is in seconds.
</Note>

#### `subscribe`

Adds types and addresses to the connection. Subscriptions add up: each call merges with what the connection already has.

| Param | Required | Description |
| ----- | -------- | ----------- |
| `types` | Yes | The types to add. |
| `addresses` | For `accounts` and `user_transactions` | The addresses to watch. |

```json
{
  "id": "4",
  "method": "subscribe",
  "params": {
    "types": ["accounts", "user_transactions"],
    "addresses": ["klv1t98a8r7ej26nmqadk8e4hykfxsm6gqelavwrt2l5z3a02xdm8xuq9cx9n5"]
  }
}
```

The reply is `{"id": "4", "data": "subscribed"}`.

Types and addresses pair up only inside one call. The addresses in a call get the `accounts` and `user_transactions` types named in that same call, and nothing else:

- A later call with only `"types": ["user_transactions"]` and no addresses does not reach the addresses you already watch. To add a type to them, send the type and the addresses again.
- A call with addresses but neither `accounts` nor `user_transactions` in `types` ignores the addresses. The reply is still `subscribed`.

The same rule applies to the subscription message that opens the connection.

#### `unsubscribe`

Removes types and addresses from the connection, and leaves the rest untouched.

| Param | Required | Description |
| ----- | -------- | ----------- |
| `types` | Yes | The types to remove. |
| `addresses` | For `accounts` and `user_transactions` | The addresses to stop watching. |

```json
{
  "id": "5",
  "method": "unsubscribe",
  "params": { "types": ["transactions"] }
}
```

The reply is `{"id": "5", "data": "unsubscribed"}`. For an address, only the named type is removed: an address watched for both `accounts` and `user_transactions` keeps the other one.

### Errors

**In the connection request.** A node that has reached its connection limit refuses the WebSocket upgrade with HTTP 503 and the body `{"error":"too many websocket connections"}`, before any message is exchanged. Wait and try again.

**In the subscription message.** The node answers with an error that has no `id` and closes the connection:

| Error | Cause |
| ----- | ----- |
| `subscribed_types must not be empty` | `subscribed_types` is missing, empty or misspelled. |
| `invalid subscription type: ...` | A type is not one of the four above. Note the plural in `blocks` and `transactions`. |
| `too many addresses in a single subscribe` | More than 10,000 addresses in the message. |
| `subscription address exceeds the maximum length of 62 bytes` | An entry in `addresses` is longer than a `klv1...` address. |

If the first message is not valid JSON, or does not arrive within 30 seconds, the node closes the connection without an error message.

**In a request.** The node answers with the error and your `id`, and the connection stays open:

| Error | Cause |
| ----- | ----- |
| `invalid json: ...` | The message is not valid JSON. The reply has an empty `id`. |
| `unknown method: ...` | `method` is not one of the four methods. |
| `missing required param: hash` | `get_transaction` without `hash`. |
| `must provide nonce or hash` | `get_block` without `nonce` or `hash`. |
| `invalid params: ...` | The request has no `params`, or a param has the wrong JSON type, such as a `nonce` sent as a string. |
| `transaction not found` | `get_transaction` with a hash the node does not have. |
| `block not found` | `get_block` with a nonce or hash the node does not have. |
| `invalid subscription type: ...` | `subscribe` or `unsubscribe` with an unknown type. |
| `too many addresses in a single subscribe: ...` | `subscribe` with more than 10,000 addresses. |
| `subscription address exceeds the maximum length of 62 bytes` | `subscribe` with an entry in `addresses` longer than a `klv1...` address. |
| `address subscription limit reached for this connection (max 50000)` | The connection already watches the maximum number of addresses. |
| `query not supported: facade unavailable` | The node does not answer `get_transaction` and `get_block` over WebSocket. |
| `internal error` | The node failed while handling the request. |

### Connection lifecycle

- The node sends a ping frame every 15 seconds and closes the connection if it gets no pong within 30 seconds. Browsers and most WebSocket libraries answer pings for you.
- To disconnect, close the WebSocket. The node drops all subscriptions of a closed connection, so subscribe again after you reconnect.
- Connections do drop: nodes restart and networks fail. Reconnect with a delay that grows after each failed attempt.

### Limits

| Limit | Value |
| ----- | ----- |
| Addresses in one subscription message or `subscribe` request | 10,000 |
| Addresses watched by one connection | 50,000 |

To watch more addresses, split them across connections. These are the node defaults. If you run your own node you can change them, along with the connection limits; see [WebSocket limits](/node-operations/securing-the-api#websocket-limits).

### Do not assume you receive every event

The feed is best effort. When the node's event queue or your connection's buffer is full, the node drops the event rather than wait for a slow client. It does not send it again and does not tell you. You also miss everything that happens while you are disconnected.

Replies to your requests go through the same per-connection buffer and are dropped the same way. A `get_block` or `subscribe` sent while your client is behind on reading can go unanswered, so give every request a timeout and send it again when the timeout expires.

To detect and repair gaps:

1. Subscribe to `blocks` and keep the `nonce` of the last block you processed.
2. Block nonces increase by one. If a block arrives with a nonce greater than the last one plus one, you missed the blocks in between.
3. Fetch each missing block with the `get_block` request, or over REST with `GET /block/by-nonce/{nonce}` on the [node API](https://node.mainnet.klever.org/swagger/index.html).
4. Do the same check when you reconnect, before you trust new events.

If you act on transactions or account changes, such as crediting a deposit, confirm them from the blocks you fetched instead of relying only on the pushed event.

### Examples

Both examples subscribe to `blocks` on mainnet, print each block and report gaps in the nonce sequence. To use testnet, change the URL to `wss://node.testnet.klever.org/subscribe`.

```go {{ title: 'Go' }}
package main

import (
	"encoding/json"
	"log"

	"github.com/gorilla/websocket"
)

const endpoint = "wss://node.mainnet.klever.org/subscribe"

type Subscription struct {
	Addresses []string `json:"addresses"`
	Types     []string `json:"subscribed_types"`
}

type Event struct {
	Type    string          `json:"type"`
	Address string          `json:"address"`
	Data    json.RawMessage `json:"data"`
	Error   string          `json:"error"`
}

type Block struct {
	Nonce   uint64 `json:"nonce"`
	Hash    string `json:"hash"`
	TxCount int    `json:"txCount"`
}

func main() {
	conn, _, err := websocket.DefaultDialer.Dial(endpoint, nil)
	if err != nil {
		log.Fatal("dial: ", err)
	}
	defer conn.Close()

	// The first message must be the subscription.
	sub := Subscription{
		Addresses: []string{},
		Types:     []string{"blocks"},
	}
	if err := conn.WriteJSON(sub); err != nil {
		log.Fatal("subscribe: ", err)
	}

	var lastNonce uint64
	for {
		_, message, err := conn.ReadMessage()
		if err != nil {
			log.Fatal("read: ", err)
		}

		var event Event
		if err := json.Unmarshal(message, &event); err != nil {
			log.Println("skipping message: ", err)
			continue
		}
		if event.Error != "" {
			log.Fatal("node error: ", event.Error)
		}
		if event.Type != "blocks" {
			continue
		}

		var block Block
		if err := json.Unmarshal(event.Data, &block); err != nil {
			log.Println("skipping block: ", err)
			continue
		}

		if lastNonce != 0 && block.Nonce > lastNonce+1 {
			log.Printf("missed blocks %d to %d, fetch them with get_block", lastNonce+1, block.Nonce-1)
		}
		lastNonce = block.Nonce

		log.Printf("block %d %s txs=%d", block.Nonce, block.Hash, block.TxCount)
	}
}
```

```js {{ title: 'JavaScript' }}
// Runs in browsers and in Node.js 22 or newer, which have WebSocket built in.
const endpoint = 'wss://node.mainnet.klever.org/subscribe'

const socket = new WebSocket(endpoint)
let lastNonce = 0

socket.addEventListener('open', () => {
  // The first message must be the subscription.
  socket.send(
    JSON.stringify({
      addresses: [],
      subscribed_types: ['blocks'],
    }),
  )
})

socket.addEventListener('message', (message) => {
  const event = JSON.parse(message.data)

  if (event.error) {
    console.error('node error:', event.error)
    return
  }
  if (event.type !== 'blocks') {
    return
  }

  const block = event.data
  if (lastNonce !== 0 && block.nonce > lastNonce + 1) {
    console.warn(
      `missed blocks ${lastNonce + 1} to ${block.nonce - 1}, fetch them with get_block`,
    )
  }
  lastNonce = block.nonce

  console.log(`block ${block.nonce} ${block.hash} txs=${block.txCount}`)
})

socket.addEventListener('close', (event) => {
  console.log('connection closed:', event.code)
})
```
